# 재접속(Reconnect) 설계

`docs/DESIGN.md` 15-7에 기록해 둔 필요성을 실제로 어떻게 구현할지 정리한 문서. 구현 전 설계 토론 내용을 그대로 남긴다 — 나중에 "왜 이렇게 했는지"를 다시 물을 필요가 없도록.

## 왜 필요한가 (재확인)

실제 친구들과 플레이하다가 두 가지를 겪었다: 실수로 뒤로가기를 눌렀다가 몇 초 안에 다시 들어와도 완전히 새 플레이어로 취급되는 것, 그리고 게임 중 F5를 누르면 원래 자리로 못 돌아오고 튕겨나가는 것. 원인은 같다 — 새 WebSocket 연결이 "예전의 그 플레이어"라는 걸 증명할 방법이 서버에 전혀 없다.

## 범위

**게임이 시작된 이후(로비 이후)만 다룬다.** 로비에서 새로고침한 사람은 잃을 상태가 없다 — 그냥 같은 방 코드로 다시 들어오면 된다. 실제로 로비 상태의 disconnect는 지금도 `players_` 목록에서 아예 제거해버리는 방식이라(재접속을 염두에 두지 않은 동작), 이 범위 밖으로 남겨두는 게 기존 동작과도 자연스럽게 들어맞는다.

## 결정된 사항

### 1. 본인 인증 — 비밀 토큰

`create_room`/`join_room`이 성공할 때 서버가 그 플레이어에게만 무작위 토큰을 하나 발급한다(`room_created`/`joined` 응답에 `token` 필드 추가). 클라이언트는 `{room_code, player_id, token}`을 `localStorage`에 저장해두고, 페이지가 다시 뜰 때 이게 있으면 `rejoin` 메시지로 셋을 그대로 서버에 보낸다. 서버는 그 방의 그 `player_id`가 실제로 그 토큰을 가지고 있는지 확인한 뒤에만 재접속을 허용한다.

**왜 `room_code`+`player_id`만으로는 안 되는가**: `player_id`는 1~6 사이의 숫자라 같은 방에 있는 다른 사람이 아무 번호나 넣어서 남의 자리를 가로챌 수 있다. 토큰은 이런 "재미 삼아 시도"를 막는 최소한의 장치다.

**왜 쿠키가 아니라 `localStorage`인가**: 이 앱은 정적 파일 서버(페이지)와 WebSocket 게임 서버가 완전히 분리돼 있고, 실제 프로토콜은 HTTP 요청/응답이 아니라 WS 메시지로 오간다. 쿠키가 자동으로 첨부되는 이점을 살릴 방법이 없고(어차피 우리 JS가 토큰을 직접 읽어서 메시지에 넣어야 함), `file://`로 직접 열었을 때 쿠키는 브라우저가 막는 경우가 흔한 반면 `localStorage`는 대체로 잘 동작한다.

**이 토큰의 보안 수준(솔직한 평가)**: 이건 정교한 인증이 아니라 "가벼운 오남용 방지"용이다. 브라우저의 출처(origin) 격리 덕분에 다른 웹사이트는 이 토큰을 절대 못 읽지만, **우리 페이지 안에 악성 스크립트가 끼어드는 경우(XSS)**엔 뚫릴 수 있다 — 그리고 실제로 지금 클라이언트에 그 구멍이 있다(아래 "부수 작업" 참고). PC에 직접 접근 가능한 사람을 막을 수는 없는데, 이건 클라이언트 저장소를 쓰는 이상 근본적으로 못 막는 문제라 파티 게임 수준에서는 감수한다.

### 2. 재접속 슬롯의 만료 — 별도 타이머 없음

방이 존재하는 한 언제든 재접속을 허용한다. 별도의 "재접속 대기 시간"을 만들지 않는 이유는 이미 있는 장치들이 자연스럽게 시간을 제한해주기 때문이다:

- 지금이 그 사람의 활성 구간(범행 작성 90초 / 추리 작성 45초)이라면, 이미 만든 `phase_timer_`가 알아서 시간 초과 처리를 하고 게임을 진행시킨다 — 재접속을 기다려주다가 게임이 멈추는 일은 없다.
- 전원이 나가면 `RoomManager`가 어차피 방 자체를 정리한다 — 그 시점 이후엔 재접속을 시도해도 방을 못 찾아서 자연스럽게 실패한다.

자기 턴이 이미 지나가 버린 뒤에 재접속하면 그냥 지금 상황을 구경하는 입장으로 돌아온다 — 이미 제출을 마친 사람과 동일한 처지.

### 3. 방장 승계는 되돌리지 않는다

방장이 끊겼다가 돌아와도 Phase 5에서 만든 승계 로직으로 이미 넘어간 방장 자리를 되찾아오지 않는다. 방장이 왔다 갔다 하는 혼란을 막고, 재접속 로직을 host 승계 로직과 엮지 않아도 되게 한다.

### 4. 같은 사람이 두 곳에서 접속하면 — 새 연결이 이긴다

`player_id`+토큰이 일치하는 새 연결이 들어오면, 그 자리에 이미 다른(살아있는) 소켓이 연결돼 있어도 새 연결이 그 자리를 차지하고 서버가 이전 소켓을 강제로 닫는다. 두 개의 탭이 같은 플레이어로 동시에 행동할 수 있는 상황을 만들지 않기 위함.

### 5. 재접속 시 서버가 다시 보내주는 것 — 전용 동기화 메시지

`room_update`/`board_info`(기존 `send_room_snapshot`)만으로는 게임 진행 중 상태를 복원하기에 부족하다. 처음엔 "예전에 왔던 메시지들을 순서대로 재생"하는 방식을 생각했는데, 각 메시지 핸들러가 "지금 막 이 일이 일어났다"는 걸 전제로 부수효과를 갖고 있어서(`your_role`이 무조건 범행 작성/대기 화면을 새로 세팅하는 것 등), 재생 방식은 순서가 안 맞으면 오히려 잘못된 화면을 만든다. 그래서 **현재 상태를 있는 그대로 담은 새 메시지 하나**를 만들기로 했다.

```json
{
  "type": "game_state_sync",
  "state": "Investigation",
  "round": 2,
  "role": "detective",
  "crime_score": 82,
  "current_detective_id": 3,
  "current_attempt": 1,
  "answer_key": null,
  "score_breakdown": null
}
```

- `role`: 게임이 진행 중이 아니면(`Lobby`/`GameOver`) `null`.
- `crime_score`: 이번 라운드에 아직 평가가 공개되지 않았으면 `null`. 이걸 판단하려면 `GameRoom`에 "이번 라운드 점수가 공개됐는가" 플래그를 하나 추가해야 한다(`crime_eval_.score`의 기본값 0과 "아직 평가 전"을 구분하기 위함).
- `current_detective_id`/`current_attempt`: `state`가 `Investigation`일 때만 채워짐.
- `answer_key`/`score_breakdown`: `role`이 `criminal`이고 이미 계산돼 있으면(`crime_eval_`에 그대로 남아있음, 재계산 불필요) 채워짐 — 범인이 자기 정답표를 다시 봄.

클라이언트는 `game_state_sync`용 새 렌더 함수 하나로 화면을 현재 상태에 맞게 직접 세팅한다(기존 이벤트 핸들러들을 재활용하지 않음).

**이번 버전에서 일부러 안 하는 것**: 재접속 시점에 진행 중이던 제한 시간(범행 작성/추리 작성)의 **남은 시간을 정확히 복원하지 않는다** — 서버는 실제 마감을 그대로 지키지만(안전에는 문제없음), 클라이언트 카운트다운은 재접속 시 다시 표시하지 않거나 처음부터 새로 보여준다. 정확한 남은 시간 복원은 서버가 타이머 시작 시각을 따로 기록해야 해서 복잡도가 늘어나는데, 지금 목표(끊겼다 금방 돌아오는 것)엔 필수가 아니라고 판단해 뺐다.

## 서버 쪽 구현 개요

- `Player`에 `token`(발급 시 무작위 문자열) 추가. **`build_room_update()`의 `players_json`에는 절대 포함하지 않는다** — 그건 방 전체에 브로드캐스트되므로, 포함하면 모든 플레이어가 서로의 토큰을 보게 된다.
- `GameRoom`에 `verify_rejoin(player_id, token)`과 `handle_reconnect(player_id)`(host는 안 건드리고 `connected = true`만 세팅) 추가.
- `GameRoom`에 `build_game_state_sync(player_id)` 추가, 위 JSON을 만듦.
- `RoomManager`에 `rejoin_room(room_code, player_id, token, session)` 추가: 토큰 검증 → 기존 소켓이 살아있으면 닫고 → `sessions[player_id]`를 새 세션으로 교체 → `GameRoom::handle_reconnect` 호출.
- `GameServer::on_message`에서 `session->room_code()`가 없을 때 `create_room`/`join_room`과 나란히 `rejoin` 처리 추가.

## 클라이언트 쪽 구현 개요

- `room_created`/`joined` 응답을 받으면 `{room_code, player_id, token}`을 `localStorage`에 저장.
- 페이지 로드 시(`connect()` 이전) `localStorage`를 확인 — 있으면 `join-screen`을 보여주지 않고 곧바로 `rejoin` 메시지를 보낸다. 실패(`error` 응답)하면 `localStorage`를 지우고 평소처럼 `join-screen`을 보여준다.
- `game_over`에서는 일부러 `localStorage`를 지우지 않는다 — `restart_game`은 새 방을 만드는 게 아니라 **같은 방(같은 player_id·토큰)을 Lobby 상태로 되돌리는 것**이라, 여기서 지워버리면 방장이 재시작한 뒤 새로고침한 플레이어가 재접속을 못 하게 된다. 저장된 세션이 정말로 못 쓰게 되는 시점(방 자체가 사라짐)은 `rejoin`이 실패할 때이므로, 정리는 그 실패 경로(`error` 처리) 하나로 충분하다.
- `game_state_sync` 핸들러 추가 — 위에서 설명한 대로 현재 상태에 맞게 화면을 직접 세팅.

## 부수 작업: XSS 이스케이프 처리

토큰을 훔칠 가치가 생기는 김에, 클라이언트가 사용자 입력을 이스케이프 없이 `innerHTML`에 그대로 꽂아 넣던 기존 구멍을 같이 막는다. 실제로 발견한 지점:

| 위치 | 값 | 출처 |
|---|---|---|
| `renderPlayers()` | `p.name` | 플레이어 닉네임 (사용자 입력) |
| `appendLogEntry()` | `name`(플레이어 닉네임), `guessLine`(`msg.guess_text`) | 닉네임, 탐정의 추리 서술 (둘 다 사용자 입력) |
| `renderCriminalAnswerKey()` | `a.answer` | AI가 생성한 요약 (범행 서술에서 파생, 간접적으로 사용자 입력 영향) |
| `renderRoundResult()` | 범인 이름, `msg.crime_text`, `msg.evaluation`, 점수 획득 목록의 이름들 | 닉네임, 범행 서술 원문(사용자 입력), AI 평가 텍스트 |
| `renderGameOver()` | 순위 목록의 이름들 | 닉네임 |

조치: 위 값들을 전부 감싸는 `escapeHtml()` 헬퍼 하나를 추가하고, 해당 지점에 전부 적용한다. `textContent`를 쓰는 곳(`turn-banner`, `waiting-message`, `advance-hint` 등)은 원래도 브라우저가 자동으로 이스케이프하므로 손댈 필요 없음 — `innerHTML`/`insertAdjacentHTML`로 문자열을 직접 조립하는 곳만 문제.

## 구현하면서 다듬어진 부분

- **`game_over`에서 `localStorage`를 지우지 않기로 바꿨다.** 처음엔 "게임이 완전히 끝났으니 지운다"고 적었는데, 막상 구현하면서 보니 `restart_game`은 새 방이 아니라 **같은 방(같은 player_id·토큰)을 Lobby로 되돌리는 것**이었다. 여기서 지워버리면 방장이 재시작한 뒤 새로고침한 플레이어가 재접속을 못 하게 된다. 대신 저장된 세션이 진짜로 못 쓰게 되는 시점(방이 사라져서 `rejoin`이 실패하는 순간)에만 지우도록 정리했다.
- **`Result`/`NextRound` 상태 재접속을 위해 `round_result`를 캐싱하도록 추가했다.** 처음 설계할 땐 빠뜨렸던 부분 — `round_result`는 그 순간 접속해 있던 사람에게만 나가는 1회성 브로드캐스트라, 그 이후 재접속하는 사람은 그 라운드의 결과를 영영 못 볼 뻔했다. `GameRoom`이 마지막 `round_result`를 그대로 들고 있다가 `game_state_sync`에 실어 보내는 방식으로 해결했다(단, 그 라운드의 탐정별 추리 로그까지는 복원하지 않는다 — 그건 클라이언트가 화면에 쌓아온 기록일 뿐 서버가 저장해두는 데이터가 아니기 때문).
- **메시지 도착 순서를 서버가 보장하지 않는다는 걸 구현 중에 발견했다.** `rejoin`이 성공하면 재접속 처리 내부에서 `room_update`를 먼저 브로드캐스트하는데, 이 시점에 재접속한 세션도 이미 등록돼 있어서 그 브로드캐스트가 명시적 `rejoined` 응답보다 먼저 도착할 수 있다. 서버 쪽에서 순서를 억지로 맞추는 대신, 클라이언트가 `rejoin`을 보내는 시점에 이미 알고 있는 `myId`를 로컬에서 먼저 세팅해두는 방식으로 이 문제를 피했다 — 어차피 재접속하려는 자기 자신의 `player_id`는 서버 응답을 기다릴 필요 없이 이미 알고 있는 값이다.

## 검증

서버 측 메커니즘(정상 재접속, 잘못된 토큰 거부, 중복 접속 시 새 연결이 이김, `Investigation`/`NextRound` 상태별 `game_state_sync` 내용)을 스크립트로 직접 재현해서 확인했다. 실제 뒤로가기/F5는 브라우저 동작이라 스크립트로 완전히 똑같이 재현하기 어렵지만, 그 두 상황이 결국 만들어내는 서버 관점의 이벤트(연결 종료 후 같은 토큰으로 새 연결이 들어오는 것)는 동일하므로 위 테스트로 충분히 커버된다.
