# Phase 6 부하 테스트 상세 기록

`docs/DESIGN.md` 4단계(부하 테스트)에서 요구한 대로, 실제 게임 플레이 규모를 넘는 동시 Room 수(10 / 50 / 100 / 500)로 서버를 몰아붙이며 CPU·메모리·메시지 처리량·AI 병목을 실측했다.

측정은 두 갈래로 나눠 진행했다.

1. **구조적 처리량 측정 (Mock 백엔드)**: AI 호출 시간이라는 변수를 완전히 제거하고, 서버 자체(연결 수락, 방 생성, 상태 머신 처리, 브로드캐스트)가 동시 Room 수가 늘어날 때 얼마나 잘 버티는지만 본다.
2. **AI 동시 처리량 측정 (실제 Ollama 백엔드, `qwen2.5:7b`)**: 여러 방이 동시에 AI를 호출할 때 실제 병목이 어디서 발생하는지, 그리고 그 병목이 게임 서버의 다른 처리까지 지연시키는지를 본다 — Phase 4(비동기 Job Queue) 필요 여부를 가르는 핵심 질문이다.

문서 구성은 Phase 5(`docs/STABILITY_ISSUES.md`)와 동일한 원칙을 따른다: **1부는 실측으로 확인된 진짜 병목**, **2부는 구조를 의심해서 측정했지만 문제가 없었던(혹은 애초에 서버 문제가 아니었던) 항목**으로 분리한다.

# 1부 — 실측으로 확인된 병목

## 1-1. AI 동시 요청 처리량 — Ollama 단일 인스턴스의 직렬화로 인한 선형 지연 증가

### 구조적 배경과 예상

`OllamaClient`는 매 AI 호출마다 새 HTTP 연결을 열어 로컬 Ollama 서버(`127.0.0.1:11434`)에 요청을 보낸다. 게임 서버 쪽에서 이 호출들은 완전히 비동기(Boost.Asio)라 여러 방이 동시에 AI를 호출해도 게임 서버 자신은 막히지 않지만, **Ollama 자체는 하나의 모델(`qwen2.5:7b`)을 하나의 GPU/프로세스에 로드해 서빙**하고 있다. LLM 추론은 본질적으로 순차적인 토큰 생성 작업이라, Ollama가 여러 요청을 받아도 내부적으로 상당 부분 직렬화해서 처리할 가능성이 높다고 예상했다 — 즉 병목이 있다면 그건 C++ 게임 서버 쪽이 아니라 **로컬 LLM 서빙 자체의 처리량 한계**일 것이라고 가정했다.

### 테스트 방법

N개의 방을 만들고(각 3명), 전부 게임을 시작해 범인 역할을 배정한 뒤, **N명의 범인이 정확히 같은 시점에** `submit_crime`을 제출하도록 만들어 N개의 `evaluator_->evaluate()` 호출이 Ollama에 동시에 들어가게 했다. 각 방의 `submit_crime` 전송 시점부터 `crime_score_revealed` 수신 시점까지 걸린 시간을 개별적으로 측정했다. N을 1 → 5 → 10 → 20으로 늘려가며 반복했다.

동시에, 이 N개의 방과는 완전히 무관한 **별도의 통제 방("Probe")**을 하나 더 만들어서, AI 요청들이 쌓여있는 동안 0.2초 간격으로 아무 상관 없는 메시지(로비에서 `restart_game` — 항상 즉시 `error`로 거부됨)를 계속 보내고 응답 시간을 쟀다. 이건 "AI 요청이 쌓여도 게임 서버의 핵심 실행 흐름(io_context)이 막히지 않는다"는 걸 실제로 증명하기 위한 대조군이다.

### 결과

| 동시 요청 수(N) | 전체 완료까지 걸린 시간 | 개별 요청 지연 시간 범위 |
|---|---|---|
| 1  | 4.62초  | 4.62초 (단일값) |
| 5  | 9.96초  | 3.75초 ~ 9.96초 |
| 10 | 24.67초 | 4.77초 ~ 24.67초 |
| 20 | 44.98초 | 4.53초 ~ 44.98초 |

N이 늘어날수록 **전체 완료 시간이 대략 N에 선형으로 비례해서 늘어난다** — 1개일 때 4.6초였던 게 20개가 몰리면 마지막 요청은 45초 가까이 기다려야 한다. 이건 예상대로 Ollama가 다중 요청을 받아도 내부적으로 거의 한 번에 하나씩(혹은 아주 제한된 병렬도로) 처리하고 있다는 뜻으로 해석했다 — 게임 서버가 요청을 더 빨리 보낸다고 해서 Ollama의 처리 속도 자체가 빨라지지는 않는다.

반면 같은 시간 동안(20개 요청이 45초에 걸쳐 처리되는 내내) 통제 방("Probe")에 보낸 218번의 무관한 메시지는 **전부 1ms 이내에 응답**했고, 5초 타임아웃에 걸린 경우는 단 한 번도 없었다.

```
control probe (unrelated room, invalid-message round trip) during the AI storm:
  218 answered, min=0ms max=1ms avg=0ms
  0 timed out (>5s, would indicate the game thread was blocked)
```

### 해석 — 이게 Phase 4를 정당화하는가?

**병목은 실재한다.** 동시에 여러 방이 AI를 호출하면 뒤로 밀린 방일수록 확실히 더 오래 기다린다. 이건 실측으로 확인된 사실이고 무시할 수 없다.

다만 이 병목의 위치가 중요하다. 통제 방 테스트가 보여주듯, **게임 서버(C++, 단일 `io_context` 스레드)는 AI 요청이 아무리 쌓여도 전혀 지연되지 않는다** — 병목은 전적으로 Ollama 프로세스 내부(모델 추론 자체의 처리량)에 있다. 이 지점에서 Phase 4가 제안하는 "AI Job Queue / AI Worker / Result Queue" 구조를 게임 서버 안에 만든다고 해도, **Ollama 자신이 초당 처리할 수 있는 추론 횟수 자체는 그대로**이므로 이 선형 지연 증가는 사라지지 않는다. Job Queue를 붙였을 때 실제로 달라지는 건 "요청을 게임 서버가 어떤 순서/정책으로 Ollama에 넘기느냐"(우선순위 조정, 과부하 시 조기 타임아웃/거절 등)이지, Ollama 자체의 추론 처리량을 늘려주지는 않는다. 처리량을 실제로 늘리려면 Ollama 인스턴스를 여러 개 띄우거나 더 강력한 GPU를 쓰는 등 **추론 서빙 계층의 확장**이 필요하며, 이건 게임 서버의 스레딩 모델과는 별개 문제다.

또한 이 테스트는 "N개의 방이 정확히 같은 순간에 AI를 호출한다"는 의도적으로 만든 최악의 시나리오라는 점도 짚어둘 필요가 있다. 실제 플레이에서는 각 방이 서로 다른 속도로 진행되고(사람이 범행을 서술하는 데 걸리는 시간이 방마다 다르다), 3~6인 규모의 방 하나에서 나오는 AI 호출 빈도 자체도 낮다(라운드당 범행 평가 1회 + 탐정 추리 판정 몇 회). 따라서 20개 방이 초 단위로 완전히 동기화되어 AI를 두드리는 상황은 실제 서비스에서 흔하지 않을 가능성이 높지만, 그럼에도 "여러 방이 우연히 겹치면 그만큼 늦어진다"는 한계 자체는 실재하므로 기록해 둔다.

**결론: 이 병목은 실재하지만, Phase 4(게임 서버 내부의 Job Queue/Worker Thread)로 해결되는 종류의 병목이 아니다.** 만약 나중에 실제 동시 사용자 수가 늘어나 이 지연이 체감될 정도로 문제가 된다면, 다음에 검토해야 할 건 "게임 서버 스레드 모델 확장"이 아니라 "Ollama 인스턴스를 몇 개 더 띄워 요청을 분산할 것인가"다.

# 2부 — 구조를 의심했지만 문제없음이 확인된 항목

## 2-1. 대규모 동시 접속 시 일부 연결 거부(`ConnectionRefusedError`) — 서버 문제 아님, 테스트 하니스의 비현실적 버스트가 원인

### 왜 의심했는가

Mock 백엔드(AI 호출 없이 순수 서버 처리량만 측정)로 10 → 50 → 100개 방까지는 아무 문제 없이 거의 선형으로 확장됐다(아래 2-2 참고). 그런데 500개 방(플레이어 소켓 1500개)을 **모두 동시에** 열도록 테스트 스크립트를 짜서 돌렸더니, 매번 14~19개의 연결이 `ConnectionRefusedError`(Windows 오류 코드 1225, WSAECONNREFUSED)로 실패했다. 실패한 방 번호는 항상 순서상 뒤쪽(450번째~500번째 부근)에 몰려 있었다.

이 패턴("뒤로 갈수록 실패")을 보고 처음에는 **`Listener`의 TCP `listen()` 백로그 큐가 가득 차서 넘치는 문제**라고 의심했다. 실제 코드를 보면:

```cpp
// 수정 전
Listener::Listener(net::io_context& ioc, tcp::endpoint endpoint, GameServer& server)
    : ioc_(ioc)
    , acceptor_(ioc, endpoint)   // 암묵적으로 SOMAXCONN(OS가 알아서 정하는 크기)으로 listen
    , server_(server)
{
}
```

`acceptor(io_context&, endpoint)` 생성자는 내부적으로 `socket_base::max_listen_connections`(=`SOMAXCONN`)로 `listen()`을 호출하는데, 이 값이 Windows에서 실제로 어느 정도의 큐 크기로 해석되는지는 문서상 명확하지 않았다. 1500개의 연결이 거의 동시에 몰리면 이 큐가 넘쳐서 뒤쪽 연결들이 거부될 수 있다고 가정했다.

### 1차 조치 (나중에 틀렸다고 판명)

`Listener`를 암묵적 생성자 대신 `open()`/`set_option(reuse_address)`/`bind()`/`listen(4096)`으로 명시적으로 구성해서 백로그를 4096으로 크게 늘렸다.

### 재현 테스트 — 조치 후에도 문제가 그대로 나타남

빌드해서 500개 방 테스트를 3번 반복했는데, 여전히 2~19개의 연결이 같은 방식으로 실패했다. **백로그를 4096으로 늘려도 문제가 사라지지 않았다** — 이건 처음 세운 가설(백로그 큐 크기 문제)이 틀렸다는 뜻이었다.

### 재진단 — 진짜 원인은 테스트 스크립트가 만든 비현실적인 순간 버스트

원인을 다시 찾기 위해, 테스트 스크립트 자체가 `asyncio.gather`로 1500개의 소켓 연결을 **말 그대로 같은 이벤트 루프 틱 안에서** 한꺼번에 열도록 짜여 있다는 점에 주목했다. 실제 서비스에서는 500개 방의 플레이어 1500명이 정확히 같은 밀리초에 접속하는 일은 일어나지 않는다 — 사람이 방을 만들고 링크를 공유하고 다른 사람이 클릭해서 들어오는 과정 자체가 시간차를 만든다. 즉 이 실패가 "서버가 실제로 감당 못 하는 부하"인지, 아니면 "테스트 스크립트가 현실에 없는 순간 동시성을 인위적으로 만들어서 생긴 문제"인지를 구분해야 했다.

이를 확인하기 위해 테스트 스크립트에 `asyncio.Semaphore`를 추가해서, 소켓 연결 자체는 최대 100개까지만 동시에 진행되도록(그 이후 단계는 그대로 완전히 동시 진행) 살짝 페이싱을 걸었다. 그리고 이번엔 **1차 조치로 늘렸던 백로그 변경을 되돌려서 원래 코드(암묵적 `acceptor(ioc, endpoint)`, OS 기본 백로그) 그대로**에 대해 다시 테스트했다.

### 결과

```
=== n_rooms=500 max_concurrent_connects=100 ===
wall clock total: 4.67s
successful rooms: 500 / 500
errors: 0
```

**원래 코드(백로그 수정 없음)에 그대로, 연결 시도만 100개 단위로 살짝 페이싱했더니 500개 방(소켓 1500개) 전부 성공했다** — 걸린 시간도 4.67초로, 백로그를 4096으로 늘렸던 버전과 거의 차이가 없었다.

이건 실패의 원인이 서버의 `listen()` 백로그 크기가 아니라, **테스트 스크립트가 로컬 루프백으로 1500개의 raw TCP 연결을 완전히 동시에(같은 순간에) 열려고 시도한 것 자체**(Windows 소켓 스택 혹은 파이썬 `asyncio` 이벤트 루프가 그 순간적 동시성을 다 처리하지 못해 일부가 거부됨)였다는 걸 강하게 시사한다.

### 최종 결론과 조치

**서버 코드는 원래대로 되돌렸다** (`git stash drop`으로 1차 조치를 폐기). 처음에 시도한 백로그 확대는 실제 원인을 해결하지 못했고(재현 테스트에서 여전히 실패), 진짜 원인은 서버가 아니라 테스트 하니스의 비현실적인 순간 버스트였다는 게 명확해졌기 때문에, 검증되지 않은 채로 남겨두는 대신 제거했다 — 실제로 필요하지도, 실제로 문제를 고치지도 못하는 코드를 남겨두지 않는다는 이 프로젝트의 원칙에 따른 결정이다.

앞으로 비슷한 부하 테스트를 다시 돌릴 일이 있다면, **연결 자체를 약간 페이싱해서(예: 동시 연결 수를 100 정도로 제한) 현실적인 동시성 패턴을 흉내내야** 이런 종류의 허위 실패를 피할 수 있다는 점을 테스트 방법론으로 남겨둔다.

## 2-2. Mock 백엔드 순수 서버 처리량 (10 / 50 / 100 / 500 Room)

### 왜 측정했는가

AI 호출 시간이라는 압도적으로 큰 변수를 빼고, 서버 자체(연결 수락 → 방 생성 → 참가자 3명 합류 → `start_game` → 역할 배정 브로드캐스트)가 동시 Room 수에 따라 얼마나 잘 버티는지를 순수하게 보기 위함이다. 이 항목은 "문제를 의심해서" 측정했다기보다 설계 문서가 요구한 규모별 기준선(10/50/100/500)을 실측으로 남기기 위한 것이라, 결과가 좋으면 "문제없음"으로 분류한다.

### 테스트 방법

각 Room에 3명씩(호스트 1 + 플레이어 2) 붙여 방을 만들고, 전원이 `start_game` 이후 `your_role`을 받는 순간까지 걸리는 시간을 쟀다. 500 Room 규모에서는 위 2-1에서 확인한 대로 연결 자체를 100개 동시 단위로 페이싱했다(그렇지 않으면 서버와 무관한 이유로 일부가 실패하기 때문). 서버 프로세스의 메모리(`WorkingSet64`)와 CPU 사용 시간을 300ms 간격으로 함께 샘플링했다.

### 결과

| Room 수 | 소켓 수 | 전체 완료 시간 | 방 1개당 시작 완료 지연(p50 / p95 / max) | 성공률 |
|---|---|---|---|---|
| 10  | 30   | 0.28초 | 0.22 / 0.22 / 0.27초 | 10/10 |
| 50  | 150  | 0.57초 | 0.44 / 0.45 / 0.45초 | 50/50 |
| 100 | 300  | 1.00초 | 0.72 / 0.86 / 0.92초 | 100/100 |
| 500 | 1500 | 4.54초 (연결 페이싱 적용) | 3.04 / 4.36 / 4.44초 | 500/500 |

메모리는 서버 시작 직후 기준선 7.1MB에서, 500 Room·1500 소켓이 한꺼번에 몰리는 순간 최대 **22.35MB**까지 올라갔다가(방들이 각자 역할 배정까지 끝나고 스크립트가 소켓을 닫으면서 `RoomManager`가 빈 방을 정리함에 따라) 다시 14MB대로 내려가는 것을 확인했다 — 방이 정리되면 메모리도 같이 줄어들어 누수 징후는 없었다. CPU는 500 Room 테스트의 4.5초 구간 동안 약 4.2초의 CPU 시간을 소모했다 — 단일 `io_context` 스레드가 그 구간 동안 거의 한 코어를 계속 쓰고 있었다는 뜻으로, 서버가 그 순간 실제로 열심히 일하고 있었음(놀고 있지 않았음)을 보여준다.

### 결론

Room 수가 10 → 500으로 50배 늘어나는 동안 완료 시간은 0.28초 → 4.54초로 대략 비례해서 늘었을 뿐, 급격한 비선형 악화(예: 특정 지점을 넘으면 갑자기 몇 배로 느려지는 현상)는 관찰되지 않았다. 메모리 사용량도 500 Room·1500 소켓 규모에서 20MB 남짓으로 매우 작다. **이 규모(설계 문서가 요구한 최대치인 500 Room)에서 서버 자체의 구조적 처리량에는 문제가 없음을 확인했다** — 별도 조치가 필요하지 않다.

# 결론 및 Phase 4 판단에 대한 최종 시사점

이번 Phase 6 부하 테스트로 얻은 실측 데이터를 Phase 5의 결론과 합치면 다음과 같이 정리된다.

- **게임 서버 자체(단일 `io_context` 스레드, 비동기 I/O 구조)는 500개 동시 Room까지 구조적으로 문제없이 확장된다.** 메모리 사용량도 작고, 처리 시간도 Room 수에 대략 비례해서 늘어날 뿐이다.
- **AI 요청이 아무리 쌓여도 게임 서버의 핵심 실행 흐름(다른 방의 메시지 처리)은 전혀 지연되지 않는다** — 이건 Phase 4가 원래 해결하고자 했던 목표("AI 요청 때문에 게임 서버의 핵심 실행 흐름이 block되지 않도록 한다")가 Phase 2의 비동기 I/O 설계만으로 이미 달성되어 있다는 걸 실측으로 재확인한 것이다.
- **진짜 병목은 Ollama의 단일 인스턴스 추론 처리량**이며, 이건 게임 서버 안에 Job Queue/Worker Thread를 만든다고 해결되지 않는다 — 해결하려면 추론 서빙 계층 자체를 확장해야 하는, 성격이 다른 문제다.
- Phase 5에서 발견된 두 실제 버그(use-after-free 크래시, 방장 승계 누락) 역시 AI 처리량과 무관한 콜백/상태 수명 관리 문제였다.

종합하면, **Phase 4(비동기 AI Job Queue)를 지금 시점에 게임 서버 안에 구현할 근거는 여전히 발견되지 않았다.** 실제로 필요해질 수 있는 시나리오는 "동시 접속 Room 수가 지금 테스트한 규모를 훨씬 뛰어넘어, Ollama 하나로는 감당이 안 되는 수준까지 커졌을 때"이며, 그때 필요한 조치도 게임 서버의 스레딩 모델 확장이 아니라 AI 추론 서빙 계층의 확장(다중 Ollama 인스턴스 등)일 가능성이 높다.
