# 살인의 추억

## 1. 프로젝트 개요

### 장르

멀티플레이어 텍스트 기반 추리 게임

### 핵심 게임 구조

한 라운드마다 한 명이 **범인**, 나머지는 **탐정**이 된다.

범인은 제공된 범행 장소와 무기 정보를 바탕으로 자유롭게 범행을 작성한다.

AI는 범행의 개연성 및 실행 가능성을 평가하여 범행 점수를 산출한다.

탐정들은 범인의 범행을 추리하고, 정해진 횟수 안에 범행 경위를 맞혀야 한다.

모든 플레이어가 한 번씩 범인이 된 후 최종 점수를 비교하여 승자를 결정한다.

---

# 2. MVP 목표

MVP의 목표는 다음 기능이 실제 플레이 가능한 수준으로 완성되는 것이다.

* 3~6명 멀티플레이
* 방 생성 및 입장
* 라운드별 범인/탐정 역할 배정
* 범행 장소 및 무기 제공
* 범인의 자연어 범행 작성
* Ollama를 이용한 범행 평가
* 탐정의 자연어 추리
* 추리 결과 판정
* 추리 시도 횟수에 따른 점수 차등
* 라운드 진행
* 최종 점수 계산
* AI Test Mode
* 기본적인 예외 상황 처리

그래픽이나 대규모 서버 최적화보다 **게임 규칙과 서버 상태 관리의 정확성**을 우선한다.

---

# 3. 전체 서버 구조

MVP의 서버는 다음 구조를 목표 구조로 한다.

```text
Browser
   │
   │ WebSocket
   ▼
┌─────────────────────────────────────┐
│           C++ Game Server           │
│                                     │
│  Network Layer                      │
│       │                             │
│       ▼                             │
│  Game Execution Thread              │
│       │                             │
│       ▼                             │
│  RoomManager                        │
│       ├── GameRoom                  │
│       ├── GameRoom                  │
│       └── GameRoom                  │
│                                     │
│       │                             │
│       ▼                             │
│  AI Job Queue                       │
│       │                             │
│       ▼                             │
│  AI Worker Thread(s)                │
└───────┬─────────────────────────────┘
        │ HTTP
        ▼
     Ollama
```

## 핵심 설계 원칙

### GameRoom 단위 상태 격리

각 게임방은 독립적인 `GameRoom` 인스턴스로 관리한다.

```text
RoomManager
 ├─ GameRoom #1001
 ├─ GameRoom #1002
 └─ GameRoom #1003
```

각 `GameRoom`은 다음 상태를 독립적으로 가진다.

* 플레이어 목록
* 현재 라운드
* 범인
* 탐정
* 게임 상태
* 턴 정보
* 범행 정보
* AI 평가 결과
* 탐정별 추리 횟수
* 플레이어별 점수

방 내부의 게임 상태가 다른 방과 직접 공유되지 않도록 한다.

# 4. 실행 모델

## MVP 초기 구현

처음부터 모든 서버 구조를 고도화하지 않는다.

1단계에서는 다음 정도로 시작한다.

```text
WebSocket
   ↓
GameServer
   ↓
GameRoom
   ↓
GameState
```

게임 로직은 단일 실행 흐름에서 처리한다.

이 게임은 3~6명의 턴제 게임이므로 게임 상태 자체를 병렬 처리할 필요가 거의 없다.

## 이후 구조 개선

기본 게임이 정상적으로 동작한 이후 다음 단계에서 구조를 확장한다.

### 단계 1 — 게임 로직 분리

```text
Network
   ↓
GameServer
   ↓
RoomManager
   ↓
GameRoom
   ↓
GameState
```

네트워크 처리와 게임 상태 관리를 분리한다.

### 단계 2 — AI 처리 분리

Ollama 요청은 게임 실행 흐름을 직접 block하지 않도록 별도의 작업 큐와 worker에서 처리한다.

```text
Game Thread
    │
    │ AI Request
    ▼
AI Job Queue
    │
    ▼
AI Worker
    │
    │ HTTP
    ▼
Ollama
    │
    ▼
AI Result Queue
    │
    ▼
Game Thread
```

게임 상태 변경은 다시 Game Thread에서 수행한다.

이를 통해 다음 원칙을 유지한다.

> 외부 I/O는 병렬적으로 처리하되, 게임 상태 변경은 통제된 실행 흐름에서 수행한다.

### 단계 3 — 안정성 검증

다음 상황을 테스트한다.

* AI 응답 지연
* AI 응답 실패
* AI JSON 형식 오류
* Ollama 연결 실패
* 플레이어 Disconnect
* 범인 Disconnect
* 탐정 Disconnect
* 중복 요청
* 잘못된 상태에서의 요청
* 방 종료 중 AI 응답 도착
* 이미 종료된 GameRoom에 대한 AI Callback

### 단계 4 — 부하 테스트

실제 게임 플레이 규모를 넘어 여러 방을 동시에 생성하여 테스트한다.

예:

```text
10 rooms
50 rooms
100 rooms
500 rooms
```

CPU, 메모리, 메시지 처리량, AI Worker 병목 등을 측정한다.

멀티스레드를 사용하는 것 자체를 목표로 하지 않고, 실제 병목과 동시성 요구를 확인한 뒤 필요한 부분만 병렬화한다.

# 5. 게임 상태 머신

```text
Lobby
  ↓
RoleAssignment
  ↓
CrimeWriting
  ↓
AIJudging
  ↓
Investigation
  ↓
Result
  ↓
NextRound
  ↓
GameOver
```

서버는 현재 상태에 따라 허용되는 요청만 처리한다.

예를 들어:

* `CrimeWriting`에서 탐정의 추리 요청 → 거부
* `Investigation`에서 범인의 범행 재제출 → 거부
* `Result`에서 새로운 추리 요청 → 거부
* `GameOver`에서 게임 상태 변경 요청 → 거부

게임 상태는 클라이언트가 결정하지 않는다.

> **Game Server가 게임의 최종 권한을 가진다.**

# 6. 범행 작성

범인은 제공된 정보를 바탕으로 자유로운 자연어로 범행을 작성한다.

범행에는 가능한 경우 다음 내용이 포함된다.

* 사용한 무기
* 범행 장소
* 살해 방법
* 이동 과정
* 범행 이후 행동
* 무기 은닉/폐기 방법

범행은 정형화된 입력이 아니라 자유로운 자연어 입력을 기본으로 한다.

이를 통해 다음과 같은 창의적인 범행이 가능해야 한다.

> "칼을 사용한 뒤 냉장고에서 연어를 꺼내 배를 갈라 칼을 그 안에 숨겼다."

---

# 7. AI 범행 평가

AI는 범행의 개연성을 0~100점으로 평가한다.

평가 요소 예시:

| 항목            | 배점 |
| ------------- | -: |
| 장소/환경 일치성     | 25 |
| 이동 및 실행 가능성   | 20 |
| 무기 사용의 개연성    | 20 |
| 범행 과정의 개연성    | 20 |
| 증거/무기 은닉의 개연성 | 15 |

AI는 단순 점수뿐만 아니라 범행의 핵심 내용을 구조화하여 반환한다.

예:

```json
{
  "score": 72,
  "evaluation": "...",
  "key_facts": [
    "...",
    "..."
  ],
  "critical_actions": [
    "...",
    "..."
  ]
}
```

---

# 8. 범행의 핵심 사실 보존

AI가 범행을 단순한 카테고리로 축약하여 핵심적인 창의적 요소를 제거하지 않도록 한다.

잘못된 예:

```text
장소: 주방
무기: 칼
은닉 장소: 냉장고
```

이것만으로는 부족하다.

다음과 같이 범행을 성립시키는 관계와 행위를 보존해야 한다.

```text
무기: 칼

범행 장소: 주방

살해 방법:
- 칼을 이용한 공격

은닉 과정:
- 냉장고에서 연어를 꺼냄
- 연어의 배를 가름
- 칼을 연어 내부에 넣음
- 연어를 다시 냉장고에 보관
```

핵심 원칙:

> **범인의 원본 자연어 범행은 최종 Truth Source로 유지한다.**

AI의 구조화 결과는 원본을 대체하지 않고, 추리 판정에 활용하기 위한 보조 정보로 사용한다.

---

# 9. 탐정 추리

탐정 역시 자유로운 자연어로 범행을 추리할 수 있도록 설계한다.

예:

> "범인은 주방에서 칼을 이용해 피해자를 찌른 뒤, 칼을 냉장고 안의 연어 배 속에 숨겼을 것이다."

탐정에게는 라운드당 최대 3회의 추리 기회를 제공한다.

---

# 10. 추리 판정

단순한 구조화 필드 일치 방식은 사용하지 않는다.

예를 들어 실제 범행이:

> "칼을 연어의 배 속에 넣어 냉장고에 숨겼다."

인 경우,

탐정이:

> "칼을 냉장고에 숨겼다."

라고 답하는 것은 부분적으로 맞았을 뿐 **정답으로 인정하지 않는다.**

AI는 탐정의 추리가 범행의 핵심 사실 및 핵심 행위를 어느 수준까지 포함하고 있는지 판단한다.

예:

```text
실제 핵심 사실
 ├─ 칼 사용
 ├─ 주방
 ├─ 냉장고
 ├─ 연어
 └─ 연어 내부에 칼을 은닉

탐정 추리
 ├─ 칼 ✓
 ├─ 주방 ✓
 ├─ 냉장고 ✓
 ├─ 연어 ✗
 └─ 연어 내부 은닉 ✗

→ 정답 아님
```

단, 부분적으로 맞힌 경우에는 AI가 그 정도를 별도로 평가할 수 있으며, MVP에서는 기본적으로 **정답/오답의 이진 판정**을 우선한다.

---

# 11. AI 호출 최적화

탐정마다 별도의 AI 요청을 보내지 않는다.

한 라운드의 모든 추리를 모아서 한 번에 AI에게 전달하는 것을 기본 구조로 한다.

```text
Crime
   +
Detective A Guess
Detective B Guess
Detective C Guess
Detective D Guess
   ↓
Single AI Request
   ↓
각 탐정의 정답 여부
```

이를 통해 AI 호출 횟수를 최소화한다.

기본적으로:

> **한 라운드 = 범행 평가 1회 + 추리 판정 1회**

를 목표로 한다.

AI 호출이 실패하더라도 게임 서버의 상태 머신이나 기본 게임 상태가 손상되지 않도록 한다.

# 12. 점수 시스템

## 범인

아무도 범행을 맞히지 못한 경우:

```text
범인 점수 += AI 범행 점수
```

탐정이 범행을 맞힌 경우에는 범인의 기본 범행 점수를 지급하지 않는다.

## 탐정

기본 보상:

```text
100 - AI 범행 점수
```

추리 시도 횟수에 따라 보상을 감소시킨다.

초기값:

```text
1회차 성공 → 100%
2회차 성공 → 90%
3회차 성공 → 80%
```

예를 들어 AI 범행 점수가 80점이라면:

```text
기본 보상 = 20점

1회차 성공 = 20점
2회차 성공 = 18점
3회차 성공 = 16점
```

여기에 정답자에게 별도의 보너스 점수를 지급한다.

보너스 값은 초기 플레이테스트를 통해 조정한다.

# 13. AI Test Mode

서버 설정으로 AI 테스트 모드를 활성화할 수 있다.

```text
AI_TEST_MODE=true
```

기본값은 `false`이다.

## false

일반 플레이에서는 AI 테스트를 위한 추가 파일 I/O를 수행하지 않는다.

## true

다음 정보를 외부 파일에 기록한다.

* timestamp
* room ID
* round
* player ID
* 범인의 원본 범행 텍스트
* AI 점수
* AI 평가
* AI가 추출한 핵심 사실
* 가능하면 AI 원본 응답

예:

```text
logs/ai_test/YYYY-MM-DD.jsonl
```

목적:

* 프롬프트 개선
* 모델 비교
* 이상한 점수 분석
* AI의 오판 사례 수집
* 핵심 사실 추출 품질 분석
* 추리 판정 정확도 분석

향후 필요하면 로그 파일 I/O도 별도의 logging queue/worker로 분리한다.

# 15. MVP 이후 확장 아이디어

## 15-1. 타겟 시스템

현재 점수 1위와 2위의 점수 차이가 일정 기준 이상 벌어질 경우, 1위 플레이어를 다음 라운드의 **Target**으로 지정한다.

예:

```text
1위: 420점
2위: 250점
차이: 170점

→ 1위 플레이어 Target 지정
```

Target은 해당 라운드에서 특별한 페널티/보상 규칙을 가진다.

### Target 규칙

범인이 작성한 범행 경위를 Target이 맞히지 못하면:

```text
Target → 점수 차감
```

Target이 범행 경위를 정확하게 맞히면:

```text
Target → 추가 보너스
```

목적은 게임 후반부의 점수 격차를 완화하고, 선두 플레이어에게 새로운 긴장 요소를 부여하는 것이다.

단, 구체적인 점수 차감량과 보너스는 플레이테스트 후 결정한다.

---

## 15-2. 범행 난이도 시스템

AI가 단순한 개연성 점수뿐 아니라 범행 자체의 추리 난이도를 평가하도록 확장한다.

예:

```text
범행 개연성: 82
추리 난이도: 65
창의성: 91
```

이를 활용하여 다양한 게임 모드를 만들 수 있다.

---

## 15-3. 범행 유형 / 테마

라운드마다 추가 조건을 제공한다.

예:

* CCTV가 존재하는 장소
* 시간이 제한된 범행
* 반드시 특정 무기를 사용
* 특정 장소에서 시작해야 함
* 특정 장소로 이동해야 함
* 증거를 남기면 안 됨

## 15-4. AI의 범행 판정 결과 공개 방식 개선

단순히 점수만 공개하지 않고 게임 종료 후:

```text
범행 개연성
환경 적합성
실행 가능성
은닉 방법
추리 난이도
```

등의 평가 결과를 보여준다.

## 15-5. 범행 리플레이

범인의 자연어 범행을 AI가 단계별 사건 기록으로 변환하여 결과 화면에서 보여준다.

예:

```text
20:13
피해자와 주방에서 만남

20:15
칼을 이용해 공격

20:17
냉장고에서 연어를 꺼냄

20:18
연어 내부에 칼을 은닉

20:19
연어를 냉장고에 보관
```

범행 자체를 하나의 이야기처럼 보여주는 기능이다.

## 15-6. AI 범행 검증과 플레이어 판정 분리

향후에는 AI가 담당하는 역할을 명확하게 분리한다.

```text
Crime Judge

```

각 AI 기능을 독립적으로 교체하거나 테스트할 수 있도록 한다.

# 16. 설계의 핵심 원칙

이 프로젝트에서 서버의 고도화는 멀티스레드 개수나 복잡한 자료구조를 늘리는 것을 의미하지 않는다.

핵심은 다음과 같다.

1. **GameRoom 단위로 게임 상태를 격리한다.**
2. **Game Server가 게임 상태의 권한을 가진다.**
3. **게임 상태 변경은 통제된 실행 흐름에서 처리한다.**
4. **외부 AI I/O는 게임 로직과 분리한다.**
5. **AI가 게임 상태 자체를 결정하지 않도록 한다.**
6. **범인의 원본 자연어 범행을 Truth Source로 유지한다.**
7. **AI의 구조화 결과가 범행의 핵심적인 창의적 디테일을 소실시키지 않도록 한다.**
8. **필요한 곳에만 멀티스레드를 적용한다.**
9. **실제 문제를 측정한 뒤 최적화한다.**
10. **MVP → 구조 개선 → 비동기화 → 안정성 → 부하 테스트 순으로 개발한다.**

이 프로젝트의 서버 포트폴리오 핵심 메시지는 다음으로 정리할 수 있다.

> **"작은 규모의 턴제 게임이라는 특성을 고려해 게임 상태는 단순하고 결정적인 실행 모델로 관리하고, 외부 AI I/O처럼 실제 병렬성이 필요한 부분만 분리하여 처리했다."**
