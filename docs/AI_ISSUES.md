# Phase 2 AI 이슈 기록

Ollama 연동(Phase 2) 이후 실제로 서버를 띄우고 플레이하면서 발견된 AI 관련 문제들과, 그걸 어떻게 진단하고 조치했는지를 시간순으로 남긴다. 코드 자체의 변경 이력은 git log에 있으니, 여기서는 "무엇이 잘못됐고 왜 그렇게 판단했는지"에 집중한다.

---

## 1. Ollama 콜드 스타트로 인한 첫 요청 타임아웃

**문제**

연동 코드를 다 붙이고 처음으로 실제 3인 게임을 스크립트로 돌려봤을 때, 추리 판정(`OllamaGuessJudge`)은 6.3초/3.6초로 정상 응답했는데 범행 평가(`OllamaCrimeEvaluator`) 쪽만 60초 타임아웃에 걸렸다.

**테스트**

3개의 WebSocket 연결로 방을 만들고, 범인이 범행을 제출한 뒤 평가 결과를 기다리는 스크립트.

**결과**

```
"evaluation": "AI 평가에 실패하여 기본 점수(50)가 적용되었습니다. (read failed: The socket was closed due to a timeout)"
```

`OllamaClient`가 설정한 60초 타임아웃(연결+요청 전송+응답 수신을 합친 예산)을 넘겨서 실패 처리(50점 기본값)로 폴백됐다.

**원인 분석**

범행 평가가 이 세션에서 Ollama에 보낸 **첫 번째** 요청이었다는 점이 핵심. 이후에 실행된 추리 판정들은 몇 초 만에 응답했는데, 이는 Ollama가 모델을 최초 요청 시점에 VRAM으로 올리는("콜드 스타트") 데 걸리는 시간이 이후의 정상 추론 시간보다 훨씬 길기 때문. 즉 코드 버그가 아니라 로컬 LLM 서빙 특성이었다.

**조치**

1. `GameServer` 생성 시점에 실제 게임과 무관한 더미 요청을 한 번 미리 보내 모델을 예열(`warm_up_ollama`).
2. 콜드 스타트가 예열로도 완전히 없어진다는 보장은 없으므로, `OllamaClient`의 타임아웃도 60초 → 120초로 늘려 안전 마진을 둠.

**재검증 결과**

서버 시작 후 콘솔에 `Ollama warm-up complete.`가 뜬 뒤 같은 시나리오를 다시 실행하니, 범행 평가가 정상적으로 85점 + 구체적인 한국어 평가 이유("범행 장소와 무기 사용은 타당하지만, 밧줄을 이용해 목을 졸랐다는 행위는 상대적으로 덜 잔혹한 묘사로 인해 개연성에서 약간의 감점을 주었다...")를 반환했다. 이후 재현되지 않음.

## 2. 흉기 선택(UI 클릭)과 범행 서술(텍스트) 불일치로 인한 오판정

**문제 (사용자 발견)**

> "실제 사용한 흉기는 총이었는데, 탐정이 촛대로 뒤통수를 쳤다고 해도 부분 평가에서 흉기는 일치라고 평가하더라."

**원인 분석**

당시 범인은 흉기를 UI에서 클릭으로 선택하고, 범행 서술은 별도의 자유 텍스트로 작성했다. 이 둘 사이를 강제로 일치시키는 장치가 없었다 — 즉 "총"을 선택해 놓고 서술 텍스트에는 둔기로 가격하는 내용을 써도 통과됐다. AI는 실제 서술 텍스트를 근거로 판단했으므로, 탐정의 "촛대" 추리가 서술 텍스트의 실제 내용과 더 가까웠다면 AI 입장에서는 합리적인 판정이었을 수 있다. **AI 판정 로직의 결함이 아니라, 두 개의 서로 다른 진실 소스(선택값 vs 서술 텍스트)가 어긋날 수 있는 게임 데이터 설계 결함**이었다.

**조치 (1차)**

`submit_crime` 처리 시 서술 텍스트 안에 선택한 흉기 이름이 실제로 포함되어 있는지 서버에서 검증하도록 추가 (장소에 이미 적용 중이던 것과 동일한 방식).

**조치 (2차, 사용자 지시)**

> "지금 범인이 흉기중에 하나를 클릭해서 선택하고 다시 텍스트 속에 녹여내야하는데, 불필요한 과정이 중복되는거 같아. 클릭은 필요 없도록 바꾸고, 텍스트로만 서술하도록 수정해줘"

흉기 선택 UI를 완전히 제거하고, 장소를 추출하던 방식(`GameData::extract_room_mention`)과 동일하게 서술 텍스트에서 흉기 이름을 추출하는 `GameData::extract_weapon_mention`을 추가. "선택값과 서술 내용이 다를 수 있다"는 문제 자체가 구조적으로 사라짐(진실 소스가 텍스트 하나로 통일됨).

**재검증 결과**

`weapon` 필드 없이 텍스트만으로 범행을 제출하는 스크립트 테스트에서 정상적으로 장소·흉기가 추출되어 `AIJudging` 상태로 전이됨을 확인. 이후 이 종류의 불일치는 재현되지 않음.

## 3. 무의미한 답변이 일부 항목에서 "유사"/"일치"로 오판정 (모델 자체의 한계 → 모델 교체)

이 항목이 Phase 2에서 가장 오래 붙잡고 있었던 문제다.

**문제 (사용자 발견)**

> "입력난에 막 의미 없는 내용, 예를 들어. 몰라. 잉? 어... 같은걸 입력하면 일부 평가 요소가 유사로 뜨는 문제가 있다."

**배경 — 왜 처음에 exaone3.5:7.8b였는가**

Ollama 모델을 고를 때, 이 게임이 한국어 자유 서술을 평가/판정해야 한다는 점 때문에 한국어 품질을 최우선으로 두고 `qwen2.5:7b`(다국어 강함)와 `exaone3.5:7.8b`(LG AI연구원, 한국어 네이티브 튜닝) 두 후보를 놓고, 사용자가 "일단 EXAONE 먼저 해보자. 해보고 좀 문제가 있다 싶으면 그때 바꿔보면 되니까"라고 결정해 exaone3.5:7.8b를 먼저 채택했다.

**1차 조치**

`OllamaGuessJudge`의 시스템 프롬프트에 명시적 규칙과 예시를 추가:

- "탐정의 추리가 그 항목에 대해 아무 내용도 제시하지 않았거나(예: '몰라', '음...', '잉?' 같은 무의미한 답변) 완전히 틀렸다면 애매하게 봐주지 말고 반드시 '불일치'로 판정하세요. 확신이 없다고 해서 '유사'를 기본값으로 쓰지 마세요."
- 구체적 예시 1개 추가: 추리가 "몰라"뿐이면 5개 항목 모두 '불일치', correct는 false여야 한다는 워크된 예시.

동시에 `OllamaClient`의 모든 요청에 `temperature: 0.2`를 적용 (판정관/평가관 역할은 창의적 생성이 아니라 일관된 채점이 목적이므로, 이 프로젝트의 모든 AI 호출에 공통으로 적용).

**테스트**

3인 방에서 범인이 "주방에서 칼로 피해자를 찌른 뒤, 냉장고 속 생선 배 안에 칼을 숨겼다"는 범행을 제출하고, 탐정이 "몰라"라는 한 단어만 추리로 제출하는 스크립트.

**결과 (1차 조치 후) — 개선 없음**

```
aspects: [
  {"aspect": "장소", "verdict": "불일치"},
  {"aspect": "무기", "verdict": "일치"},        ← 틀림: "몰라"에는 흉기 정보가 전혀 없음
  {"aspect": "살해 방법", "verdict": "유사"},   ← 틀림
  {"aspect": "은닉 장소", "verdict": "불일치"},
  {"aspect": "은닉 방법", "verdict": "불일치"}
]
correct: false
```

프롬프트 수정과 temperature 조정을 적용하기 **전과 완전히 동일한(바이트 단위로 같은) 결과**가 나왔다. 이건 샘플링 변동성의 문제가 아니라, exaone3.5:7.8b가 이 판단 자체를 일관되게(그리고 잘못) 내리고 있다는 뜻으로 판단했다 — 즉 프롬프트를 더 다듬어서 고칠 수 있는 문제가 아니라 이 체크포인트의 능력 한계일 가능성이 높다고 결론.

**사용자 지시**

> "qwen2.5:7b로 바꿔서 비교해보기"

**조치**

`qwen2.5:7b`(4.7GB) 다운로드 후 `MOM_OLLAMA_MODEL` 환경변수만 바꿔서(코드 변경 없음 — 애초에 이 교체가 쉽도록 환경변수로 모델을 선택하게 만들어 둔 덕분) 동일한 프롬프트·동일한 temperature·동일한 테스트 시나리오로 재실행.

**재검증 결과**

- **무의미한 답변 테스트**: 같은 "몰라" 입력에 대해 5개 항목 전부 정확히 `불일치`, `correct: false`.
- **정답 판정 테스트(회귀 확인)**: 원문을 그대로 베끼지 않고 다르게 표현한 정답 추리("범인은 정원에서 밧줄로 피해자의 목을 졸라 죽인 뒤, 그 밧줄을 토막 내서 화단 흙에 파묻어 감췄을 것이다")에 대해서도 5개 항목 전부 `일치`, `correct: true`로 정확히 판정 — qwen으로 바꿨다고 판정이 전반적으로 더 엄격해지기만 한 게 아니라, 맞는 건 여전히 맞다고 판단함을 확인.
- **범행 평가 품질**: 같은 시나리오에서 크라임 스코어 82점 + "정원에서 범행을 저지른 것은 지도상의 위치와 일치하며... 밧줄을 잘게 잘라 화단 흙 속에 숨기는 것은 상당히 복잡한 행동으로, 범행 후의 행동이 조금 과장되어 보입니다" 같은 합리적인 한국어 평가 근거도 정상적으로 나옴.

**최종 조치**

기본 모델(`MOM_OLLAMA_MODEL`의 기본값)을 `exaone3.5:7.8b` → `qwen2.5:7b`로 변경. `exaone3.5:7.8b`는 삭제하지 않고 그대로 남겨서, 필요하면 환경변수 하나로 언제든 되돌리거나 다시 비교할 수 있게 해뒀다.

**결론**

- 프롬프트 엔지니어링과 temperature 조정만으로는 고쳐지지 않는, 모델 자체의 판단 편향이 존재할 수 있다 — 이번 경우 "확신이 안 서면 후하게 준다"는 성향이 exaone3.5:7.8b 쪽에 강하게 박혀 있었던 것으로 보인다.
- 이런 상황을 빠르게 검증할 수 있었던 건 애초에 AI 백엔드를 인터페이스(`ICrimeEvaluator`/`IGuessJudge`)로 추상화해두고, 모델/백엔드를 환경변수로 고르게 만들어둔 설계 덕분 — 코드 변경 없이 모델만 바꿔서 같은 테스트를 재실행할 수 있었다.
